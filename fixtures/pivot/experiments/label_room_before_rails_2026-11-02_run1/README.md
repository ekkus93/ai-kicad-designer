# Net labels given room before and after the rails (2026-11-02)

The designs were generated by `NativeSchematicEngine._compile` (brief v3 power-symbol rails) from the working tree committed as `d7a0703f`. They were then assessed with `NativeSchematicEngine.assess` on this Linux host (KiCad 10.0.6 via `/tmp/AppDir/AppRun`), which is not the locked qualification host.

**Why the step now runs twice:** `clear_label_pin_numbers_text` used to run only after rail planning. On inverting_gain the VPLUS rail had already been routed one grid step outside the VMINUS stub, so the label could not move, and VMINUS stayed 0.14 mm from J1 pin number 4. The step now runs on the compiler output, so the rails route around the longer stub. It runs again after the rails for designs where rail planning moves a part to where its labels have room (sallen_key's J1).

**Results:**
- VMINUS clears J1 pin number 4 by 1.41 mm on every op-amp connector that has the label. That includes inverting_gain, where the VPLUS rail now drops at x 24.13 instead of 25.4.
- Compared with `review_loop_corpus_v3_2026-11-02_qwen35_32k_run1`, ignoring UUIDs:
  - sallen_key is identical.
  - dual_buffer and noninverting_gain change only in wire order.
  - rc_to_buffer attaches one VMINUS rail wire at x 26.67 instead of 30.48.
  - dual_rail_reference's VMINUS power symbol sits one grid step further out.
- The other nine corpus designs were regenerated with the label step before the rails only, and were byte-identical to run1 apart from UUIDs. The second pass after the rails reproduces the previous pipeline, which moved no labels on them, so they are not repeated here.
- `assessment.json`: every independent check passes for all six designs.
- inverting_gain's VMINUS flag still points down. Turning it left would cross the VPLUS rail.
- No model review has been run: the Ollama server is offline.
